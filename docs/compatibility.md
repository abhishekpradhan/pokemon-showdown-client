# Compatibility

Showdown Arena supports the workflows below in current Chrome/Edge, Firefox and Safari, including Android Chrome and iOS Safari. It is an independent client, not a copy of every screen in the official client: the server stays authoritative for rules, validation and legal choices, and the client never invents mechanics it has not been told about. Behaviour is compared against the official client at commit [`ac7d535b`](https://github.com/smogon/pokemon-showdown-client/tree/ac7d535b28574ea3b48d5a4d1fbf6ca399abf469) (2026-08-22); the protocol and data packages are pinned in `package-lock.json`. That baseline sets regression expectations and is not a promise about every future server change.

| Workflow                   | Support                                                                                             | Verified by                                                                                                    |
| -------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Guest naming               | Supported through signed assertions                                                                 | Named handshake, denial, timeout and reconnect                                                                 |
| Registered login           | Supported when an OAuth client ID is configured for the origin                                      | Popup success/cancel/block, stale session rejection, refresh and logout races                                  |
| Matchmaking and challenges | Supported for every format the server advertises that the client can play                          | Team selection, rejection, cancellation, accept/decline, controlled real battle                                |
| Battle decisions           | The server request drives available mechanics and legal choices                                     | Singles, doubles, triples, multi and free-for-all; forced switch, preview and targets; affected generations and modifiers |
| Unsupported layouts        | Visibly gated with an explanation rather than shown as playable                                     | Capability-gate fixtures and recovery to supported formats                                                     |
| Spectating                 | Supported from any viewpoint; unrevealed information stays unknown                                  | p1–p4 and spectator projection, public/private HP, joining and rejoining mid-battle                            |
| Team building, import and export | Local workflow; the server validates format legality                                          | Lossless supported fields, generation-aware editor, file and backup round trips, failed saves and migration    |
| Chat and PMs               | Supported within server capabilities                                                                | Navigation, unread state, PM reopen and deep links, formatting and safe interactive content                    |
| Room-specific HTML         | Safe subset                                                                                         | Representative intros and polls plus malicious CSS, command and large-payload fixtures                         |
| Tournaments                | Server-driven room UI; supported formats follow battle capabilities                                 | Signups, challenge/accept, bracket updates, elimination and round-robin fixtures                               |
| Ladders                    | Public or configured endpoint, independent of the socket host                                       | Loading, paging and search where offered, empty/error states, custom endpoint                                  |
| Replays                    | Load from text or URL, playback, download and server-confirmed sharing                              | Private URLs, upload errors, seeking, long logs, imported metadata                                             |
| Personal preferences       | Public avatars, translated server messages and local backgrounds; the interface is English          | Server acknowledgement and reconnect, bounded storage and failures, readable themes                            |
| Audio and notifications    | Optional; browser permission and autoplay rules apply                                               | Separate levels, music focus/visibility/end lifecycle, keyboard and pointer unlock, unavailable audio, background notifications |
| Offline                    | Local app and team tools after installation completes                                               | Offline restart, editor, save and export; failed installation and upgrade recovery                             |
| Browsers                   | Current stable Chrome/Edge, Firefox and Safari; Android Chrome and iOS Safari                       | Chromium, mobile emulation, Firefox and WebKit flows; real-device spot checks at release                       |
| Accessibility              | Keyboard, labelled controls, visible focus, reduced motion, light/dark contrast                     | axe plus manual keyboard and screen-reader review of changed workflows                                         |

Account registration and password recovery stay on the official provider's website. Server moderation tools and community-specific commands are not automatically client features. Background push and packaged desktop clients are not planned. Live play, authentication and replay upload are not possible offline.

Rotation is unsupported until the server offers a playable rotation format and request protocol ([#14](https://github.com/abhishekpradhan/pokemon-showdown-client/issues/14)). Physical phones and screen readers are covered by emulation and manual review, not hardware acceptance; that work is tracked in [#12](https://github.com/abhishekpradhan/pokemon-showdown-client/issues/12) and described in [testing](testing.md).

## Keeping up with upstream

[@abhishekpradhan](https://github.com/abhishekpradhan) reviews protocol and data dependency updates and the daily public handshake result. A new upstream protocol or mechanic gets a fixture, an explicit capability decision, updated UI and tests, and an entry in this table. A successful handshake does not validate every battle mechanic.

A release is supported for the workflows its release notes record as verified. Anything incomplete is documented as partial or unavailable with a specific user-facing restriction, never hidden behind a claim of full parity with the official client.
